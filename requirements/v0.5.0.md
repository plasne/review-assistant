## Product Goal

Enable SMEs to configure feedback workflows on a per-project basis, record feedback and edits with user attribution and timestamps, and display historical feedback in a collapsible timeline so reviewers can see the evolution of record assessment without cluttering the current UI.

## Delta From v0.4.0

v0.4.0 provided a local tool runtime and MCP bridge for record access. v0.5.0 adds the configuration and feedback capture layer.

Newly in scope:

- A project-level feedback configuration screen with field-level feedback mode selection.
- User authentication via USERNAME environment variable.
- Storage of feedback, edits, and comments as timestamped, attributed properties on records.
- UI display of historical feedback in collapsed panels per property.
- Validation that USERNAME is present before allowing feedback submission.

Still out of scope:

- Multi-user conflict resolution or approval workflows.
- Feedback export or reporting dashboards.
- Real-time sync of feedback across multiple users.
- Audit log of all configuration changes.

## Functional Requirements

### Feedback Configuration Screen

- The app must display a project-level feedback configuration screen accessible from the project view.
- Configuration is based on the project's `config/schema.json` top-level properties and nested object properties.
- Each configurable property must have rows showing:
  - **TARGET**: Property path (e.g., "Executive Summary", "Request > Original Query", "Answer > Key Points").
  - **TAB**: Which tab the property appears on (e.g., "Main", "inherit").
  - **FEEDBACK**: Feedback mode selector with options: `none`, `good_fair_bad`, `thumbs`, `stars_5`, `text_only`.
  - **SME COMMENTS**: Checkbox to enable/disable SME comment capture for the property.
  - **EDITABLE**: Checkbox indicating whether the property is editable in the feedback flow.
- Configuration must be persisted to the project as `config/config.json` under its `properties` object.
- The configuration screen must load the current `config/config.json` on open, or provide sensible defaults if the file does not exist.
- Properties not present in the schema must be ignored.

### User Attribution via Environment Variable

- Users must set a `USERNAME` environment variable in their `config/.env` file before submitting feedback or making edits.
- If USERNAME is not set or is empty, the app must prevent feedback submission and display a validation message: "USERNAME environment variable not configured. Please set USERNAME in your config/.env file."
- The USERNAME must be visible in the UI so users know whose feedback is being recorded.
- USERNAME changes (e.g., via `config/.env` reload) must be reflected immediately without requiring an app restart.

### Feedback and Edit Storage

- Feedback, edits, and comments must be stored as additional properties on the record, separate from the record's core data.
- Properties must follow the naming convention: `_feedback_{property_name}` (underscore-prefixed to indicate system metadata, not rendered in record UI).
  - Example: If the property is "answer", the feedback property is `_feedback_answer`.
- Each entry in the feedback array is a consolidated object containing any combination of:
  - **feedback** (optional): The feedback value (rating, enum, or text depending on feedback mode).
  - **edit** (optional): Edited value for the property.
  - **comment** (optional): User comment or note.
  - **username**: The USERNAME of the user who submitted it.
  - **timestamp**: ISO 8601 UTC timestamp of when the entry was created.
- Each entry must have at least one of: `feedback`, `edit`, or `comment`.
- Example structure:
  ```json
  {
    "id": "q01",
    "question": "What is...",
    "answer": "The answer is...",
    "_feedback_answer": [
      {
        "feedback": "good",
        "username": "alice@example.com",
        "timestamp": "2026-06-01T14:32:15Z"
      },
      {
        "comment": "Needs more detail on the technical aspects.",
        "edit": "Revised answer with more detail",
        "username": "bob@example.com",
        "timestamp": "2026-06-01T15:45:22Z"
      },
      {
        "feedback": "fair",
        "comment": "Good but could be clearer",
        "username": "alice@example.com",
        "timestamp": "2026-06-01T16:20:00Z"
      }
    ]
  }
  ```

### Feedback UI and Display

- When a property is selected for review, display a feedback input panel showing:
  - The configured feedback mode for that property (or "no feedback configured" if mode is `none`).
  - A comment input field if SME comments are enabled for the property.
  - An edit input field if the property is marked editable in the configuration.
- After submission, display a collapsible "History" or "Previous Feedback" panel that shows all previous entries for that property.
- History must be collapsed by default to keep the UI clean.
- Each history entry must display:
  - The entry value (feedback, edit, or comment).
  - The username who submitted it.
  - The timestamp formatted in a human-readable relative format (e.g., "2 days ago").
- The history must be sorted with the most recent entry at the top.

### Storage Adapter Integration

- The storage adapter must handle read and write of feedback properties transparently.
- Feedback properties must not be exposed through the public `readRecord` tool to prevent leaking review state to agents.
- Feedback properties must be preserved when records are updated or migrated.

## Validation Requirements

- USERNAME must be non-empty and match a basic email or identifier pattern (e.g., `[a-zA-Z0-9._@-]+`).
- Feedback values must be non-empty strings.
- Timestamps must be valid ISO 8601 UTC format.
- Feedback properties must be arrays of objects, or an empty array if no entries exist.

## Test and Harness Requirements

- Unit tests must cover:
  - Loading and parsing `config/config.json` configuration.
  - Detecting missing USERNAME and blocking submission.
  - Validating USERNAME format.
  - Creating feedback entries with correct schema (value, username, timestamp).
  - Merging feedback properties into records without corrupting core fields.
- Integration tests must cover:
  - End-to-end feedback submission and history retrieval.
  - Storage adapter preserving feedback on record updates.
  - Configuration changes propagating to the UI.
- UI tests must cover:
  - Configuration screen rendering with schema-derived rows.
  - Feedback mode selectors and SME comment checkboxes.
  - Feedback input blocking when USERNAME is missing.
  - History panel toggling and timestamp display.
- E2E tests must cover:
  - A user setting USERNAME, configuring feedback modes, and successfully submitting feedback.
  - Subsequent users seeing historical feedback in the collapsed history panel.
  - Configuration changes taking effect on subsequent feedback submissions.
- Smoke checks must verify feedback properties are not leaked through `readRecord`.

## Acceptance Criteria

v0.5.0 is complete when:

- A project manager can configure feedback modes per property in a dedicated screen and save the configuration.
- Users with a valid USERNAME environment variable can submit feedback, edits, and comments.
- Feedback is stored on records with user attribution and timestamps.
- Historical feedback is displayed in a collapsed panel that expands on demand.
- Feedback submission is blocked with a clear error if USERNAME is not set.
- `readRecord` and other agent tools do not expose feedback properties.
