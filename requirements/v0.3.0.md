## Product Goal

Move from deterministic local echo behavior to a real agent integration in v0.3.0 by wiring chat to GitHub Copilot, while keeping the architecture ready for future backends like Azure Foundry Agents and Copilot Studio Agents without major refactoring.

## Key Decisions Captured

- v0.3.0 implements one real backend: GitHub Copilot.
- v0.3.0 keeps one active provider at a time.
- The provider abstraction should be lightweight, not a heavy plugin framework in this release.
- Chat responses must stream in v0.3.0.
- Chat history remains non-persistent in v0.3.0.
- If the backend is unavailable, show a clear error and disable chat send until recovery.
- Use the existing process-isolated bridge pattern as the first production path.

## In Scope for v0.3.0

- Replace the deterministic local echo response path with a real GitHub Copilot response path.
- Preserve strict Electron boundaries:
  - Renderer remains UI-only.
  - Main process owns orchestration, routing, and policy.
  - Process-isolated worker owns backend invocation.
- Add response streaming from backend to renderer.
- Keep current record review workflow and schema-driven read-only details behavior.
- Keep current project model and storage behavior unchanged for local and Azure project backends.
- Add clear runtime states for agent availability, in-progress generation, cancellation, and failure.
- Introduce a minimal provider contract that supports one active provider now and future provider swaps later.
- Keep deterministic harness and test gates aligned with the changed agent behavior.

## Out of Scope for v0.3.0

- Simultaneous multi-provider operation.
- Persisted chat history.
- Full plugin marketplace or dynamic third-party extension loading.
- Production implementation of Azure Foundry Agents or Copilot Studio Agents.
- Tool approval workflows, prompt management UI, or advanced conversation memory controls.

## Functional Requirements

### Agent Provider Model

- The system must expose one active provider slot at runtime.
- The initial active provider in v0.3.0 must be GitHub Copilot.
- The runtime must support replacing the active provider through main-process configuration without renderer refactoring.
- Provider-specific logic must not leak into renderer components.

### Lightweight Provider Contract

Define and use a minimal, stable provider contract in main/worker code. The contract should include:

- Provider metadata and health status retrieval.
- Streaming chat invocation.
- Cancellation support.
- Standardized error envelope for user-safe rendering and log-safe diagnostics.

The contract should be intentionally small and focused on current use cases, while leaving room to add optional capabilities later.

### Chat Request and Context Packaging

- Every chat request must include:
  - User message.
  - Selected project identifier.
  - Selected record identifier when available.
  - Selected record JSON payload when available.
  - Project `config/prompt.md` content when available.
- Context assembly must happen outside renderer business logic.
- Context packaging must be backend-agnostic at the orchestration layer.

### Streaming Behavior

- Responses must stream incrementally to the renderer.
- Renderer must display partial output as it arrives.
- Users must be able to cancel in-progress generation.
- Canceling must stop backend generation and release related runtime resources.

### Availability and Failure Behavior

- If GitHub Copilot backend is unavailable, the UI must:
  - Surface a clear, actionable error state.
  - Disable send actions while unavailable.
- The app must not silently fall back to deterministic echo behavior in v0.3.0.
- Failures must return structured errors to renderer and structured diagnostics to logs.

### Authentication Expectations

- v0.3.0 assumes user sign-in and auth context are already available through local tooling or runtime context.
- v0.3.0 does not implement a full in-app sign-in flow.
- When auth is missing or invalid, the app must show clear remediation guidance in the error state.

## Architecture Requirements

### Process Boundaries

- Renderer owns only presentation and interaction state.
- Preload exposes typed, allowlisted IPC surfaces only.
- Main process owns:
  - Provider selection.
  - Request validation.
  - Context assembly policy.
  - Stream lifecycle management.
  - Error normalization.
- Agent worker owns backend transport and protocol details.

### IPC and Streaming Contracts

- Add or update typed IPC channels for:
  - Start streamed chat.
  - Stream chunk delivery.
  - Completion event.
  - Error event.
  - Cancellation request and acknowledgement.
- Any new preload invoke or event bridge must have matching main-process registration and smoke coverage.

### Extensibility Without Heavy Frameworks

v0.3.0 must prepare for future providers by enforcing these constraints:

- Provider transport code is isolated in provider-specific modules.
- Shared orchestration and UI logic must depend only on the lightweight contract.
- Adding a new provider in a future release should primarily involve:
  - Implementing the contract in a new provider module.
  - Registering provider metadata and selection.
  - Adding provider-specific tests.

## Local Tools Surface Direction

Future versions are expected to support local function tools that can be used regardless of backend. To avoid architectural lock-in, v0.3.0 should introduce a non-breaking foundation:

- Define an internal, backend-neutral tool invocation shape in shared types.
- Keep tool execution ownership in main process (never renderer).
- Do not require full tool runtime implementation in v0.3.0.
- Ensure provider contract design can evolve to optionally advertise and invoke tools in later versions.

If pluggable tool capability is implemented in a follow-up release, the first required tool must support reading record contents for the currently selected project and record.

### First Tool Expectation for v0.3.x Follow-Up

- Define a backend-neutral `readRecord` tool capability that returns record contents for the current UI selection context.
- Enforce project isolation and existing record validation rules when resolving record content.
- Keep the tool invocation contract compatible across current and future providers.
- Return structured errors for missing records, invalid identifiers, and backend access failures.

### Example `readRecord` Tool Contract

Use the following example contract shape as the baseline for implementation and tests. Field names can evolve, but semantics should remain stable.

Request example:

```json
{
  "tool": "readRecord",
  "requestId": "req_01JX7E4N4K1S9B2K7A3Q",
  "arguments": {
    "includeSchema": false
  }
}
```

Successful response example:

```json
{
  "requestId": "req_01JX7E4N4K1S9B2K7A3Q",
  "ok": true,
  "result": {
    "projectId": "agent01",
    "recordId": "q12",
    "contentType": "application/json",
    "record": {
      "question": "...",
      "answer": "...",
      "evidence": []
    }
  }
}
```

Error response example:

```json
{
  "requestId": "req_01JX7E4N4K1S9B2K7A3Q",
  "ok": false,
  "error": {
    "code": "RECORD_NOT_FOUND",
    "message": "Record q12 was not found in project agent01.",
    "retryable": false
  }
}
```

Contract requirements:

- `requestId` must round-trip from request to response for tracing.
- Selected project and record must come from trusted UI selection context rather than tool arguments.
- Tool execution must validate the selected project and record with the same isolation and identifier rules used by existing storage flows.
- Error `code` values must be stable and documented for UI behavior mapping.
- Tool responses must never expose secrets, backend credentials, or raw filesystem/container paths.

## User Experience Requirements

- Show agent status in chat UI:
  - Ready.
  - Streaming.
  - Canceled.
  - Error.
- Maintain responsive UI during long-running streams.
- Preserve no-persistence behavior for chat state.
- Keep keyboard accessibility intact for chat input, send action, and cancellation action.

## Observability and Diagnostics

- Log provider selection and availability transitions.
- Log request lifecycle milestones with correlation identifiers.
- Redact sensitive data from logs.
- Avoid logging full record payload content unless explicitly gated for diagnostic mode.

## Test and Harness Requirements

Update behavior-focused tests to cover v0.3.0 changes:

- Unit tests:
  - Provider contract adapters.
  - Error normalization.
  - Stream state reducers.
- Integration tests:
  - Main to worker streaming pipeline.
  - Cancellation propagation and cleanup.
  - Unavailable backend error gating.
- UI tests:
  - Incremental rendering of streamed output.
  - Disabled send on unavailable backend.
  - Recovery to ready state.
- E2E and smoke:
  - IPC channel pairing for all new stream/cancel channels.
  - End-to-end streamed response happy path.
  - End-to-end auth-missing or backend-unavailable error path.

Required verification commands remain:

- `npm run lint`
- `npm run typecheck`
- `npm run test:unit`
- `npm run test:integration`
- `npm run test:ui`
- `npm run test:e2e`
- `npm run smoke`

## Acceptance Criteria

v0.3.0 is complete when all criteria below are met:

- Chat uses real GitHub Copilot backend instead of deterministic local echo.
- Streamed responses render incrementally in the UI.
- Cancellation works and stops backend work.
- Backend unavailability yields clear UI error and disabled send behavior.
- Renderer remains free of backend-specific logic.
- New streaming IPC surfaces are typed, allowlisted, and smoke-verified.
- Existing deterministic harness commands pass with updated tests.
