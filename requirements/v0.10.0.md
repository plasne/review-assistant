## Summary

This release captures the implemented hard-cut consolidation of app and project metadata into `config/` folders. Earlier requirements describe individual behaviors for schema, project configuration, prompts, MCP, environment variables, and tags. v0.10.0 defines the current filesystem and blob layout that those behaviors now share.

## Scope

### In scope

- A single `config/` directory for app-level and project-level control files.
- Hard-cut file renames with no legacy compatibility or migration code paths.
- Local and Azure storage parity for project config blob/file names.
- Symlink rejection for local project config boundaries and sensitive config files.
- Updated ignored-file behavior for environment and local MCP secrets.
- Test fixture and sample data conversion to the current layout.

### Out of scope

- Runtime migration from legacy filenames.
- Backward-compatible loading of legacy project metadata.
- User-facing UI for editing app-level config files.
- Moving review records out of the project root.

## Config layout

### App-level config directory

- App-level configuration lives in an app `config/` directory.
- By default, the app environment file is `config/.env` relative to the current working directory.
- App companion files are resolved beside the effective app env file.
- App-level companion files include:
  - `mcp.json`
  - `prompt.md`
  - `tags.json`
  - `*.mjs` computed tag plug-ins

### Project-level config directory

Every project uses a `config/` directory for project metadata:

| Path | Requirement |
| --- | --- |
| `config/.env` | Optional project environment overrides. |
| `config/schema.json` | Required JSON Schema for project records. |
| `config/config.json` | Optional project review, display, feedback, and canonical mapping configuration. |
| `config/mcp.json` | Optional project MCP server definitions. |
| `config/prompt.md` | Optional project prompt appended after the app prompt. |
| `config/tags.json` | Optional project manual tag definitions. |

Project review records remain project-root `*.json` files.

## Hard-cut legacy removal

- The app must not read or write legacy project metadata filenames.
- Legacy names include `_schema.json`, `_config.json`, `_mcp.json`, `_prompt.md`, `_prompt.txt`, and `tags/manual.json`.
- New local projects must create `config/schema.json` and `config/config.json`.
- Saving generated schemas must replace `config/schema.json`.
- Schema backups must be written as `config/schema_1.json`, `config/schema_2.json`, and so on.
- Missing required schema errors must reference `config/schema.json`.
- There is no migration code because Review Assistant is treated as greenfield.

## Environment configuration

- App startup must load app settings from the effective app `config/.env`.
- Project settings must load from the selected project's `config/.env`.
- Project-level env values may override app-level non-backend values.
- Project-level `config/.env` must not override backend selection keys:
  - `AZURE_STORAGE_ACCOUNT_CONNSTRING`
  - `AZURE_STORAGE_ACCOUNT_NAME`
  - `LOCAL_PATH`
- The local backend must also merge runtime app env-file values when loading project config so changes to app `config/.env` can be reflected without restarting.
- Environment files must reject invalid lines and invalid variable names.
- Secret-like values must be redacted in logs and renderer-visible configuration.

## Prompt, MCP, and tag loading

### Prompt loading

- App-level `prompt.md` is loaded from the app config directory when present.
- Project-level `config/prompt.md` is loaded from the selected project when present.
- Chat prompt context must append project prompt content after app prompt content.
- Prompt loading must be owned by main-process code.

### MCP loading

- App-level `mcp.json` is loaded from the app config directory when present.
- Project-level `config/mcp.json` is loaded from the selected project when present.
- Project MCP server definitions override app definitions with the same server id.
- MCP placeholder expansion must use project/app config values and process environment at chat start.
- Missing placeholder values and invalid MCP shapes must fail clearly before chat starts.

### Tag loading

- Project-level manual tag definitions are loaded from `config/tags.json`.
- App-level manual tag definitions are loaded from the app config directory `tags.json`.
- Manual tag definitions load in deterministic order with project definitions first.
- Computed tag plug-ins are loaded only from app-level `*.mjs` files in the app config directory.
- Project-level JavaScript files under `config/` are data-only and must not be executed.

## Local filesystem safety

- A project `config/` path must be a real directory when it exists.
- A project `config/` path must not be a symlink.
- Local reads and writes for project config files must reject symlinked files for:
  - `config/.env`
  - `config/schema.json`
  - `config/config.json`
  - `config/mcp.json`
  - `config/prompt.md`
- Environment file loading must reject symlinked env files.
- Path construction must remain contained under the selected project and storage root.
- Renderer code must not access config files directly.

## Azure storage parity

- Azure project containers must use the same logical paths as local projects:
  - `config/.env`
  - `config/schema.json`
  - `config/config.json`
  - `config/mcp.json`
  - `config/prompt.md`
  - `config/tags.json`
- Azure project creation must initialize `config/schema.json` and `config/config.json`.
- Azure schema save and backup behavior must match local storage naming.
- Azure prompt, MCP, env, config, schema, and tags behavior must match local storage where backend capabilities permit.

## Repository hygiene

- Real env files must be ignored through `**/.env`.
- Local MCP config containing customer-specific commands or secrets must remain ignored.
- Test fixtures may explicitly unignore tracked env fixtures needed for deterministic tests.
- Repository sample data and test fixtures must use the current `config/` layout.
- Documentation must use current paths and must not instruct users to create legacy metadata files.

## Test and harness requirements

- Unit tests must cover:
  - Config-path validation and user-visible validation messages.
  - MCP parsing and errors that reference `config/mcp.json`.
  - Tag definition loading and computed plug-in discovery from app config only.
  - Rejection or reporting of malformed computed tag plug-ins.
- Integration tests must cover:
  - Local project creation using `config/schema.json` and `config/config.json`.
  - Loading schema, project config, project env, project prompt, project MCP, and project tags from `config/`.
  - Saving generated schemas and backups under `config/`.
  - Symlink rejection for project `config/` and sensitive local config files.
  - Ignoring project-level executable JavaScript plug-ins.
- UI tests must cover:
  - USERNAME validation messages that direct users to `config/.env`.
  - Behavior that depends on project config loaded from `config/config.json`.
  - Tag editing and presentation using definitions from `config/tags.json`.
- E2E and smoke tests must cover:
  - Real Electron startup using an app-level `config/.env`.
  - Preload/main IPC behavior with the current config layout.
  - Project fixture loading from `config/` paths.
- `npm run check` must remain the deterministic gate for this surface.

## Acceptance criteria

1. All app and project metadata files use the `config/` layout described in this document.
2. No application code reads or writes legacy metadata paths.
3. New projects initialize with `config/schema.json` and `config/config.json`.
4. Local and Azure adapters use matching logical paths for env, schema, config, MCP, prompt, and tag files.
5. Project config directories and sensitive local config files reject symlinks.
6. App-level companion files resolve beside the effective app `config/.env`.
7. Computed tag plug-ins execute only from the app config directory.
8. Manual tag definitions load from `config/tags.json`.
9. Documentation and fixtures use current paths only.
10. The full deterministic check passes.
