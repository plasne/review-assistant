## Summary

This version introduces an inference harness so we can run the agent on a curated ground truth set and capture reproducible run artifacts.

This version does not score results. It only creates structured run outputs that a later evaluation system can consume.

## Application Mode

Inference is a special execution mode of the existing application and harness, not a separate application.

When inference mode is enabled:

- execution runs only the ground truth inference workflow
- tool routing uses the same group `config/` conventions as regular project paths, plus deterministic search fixtures when configured
- run controls are enforced (generated epoch run folder, `ITERATIONS`, and 10-minute timeout)
- outputs are uploaded to the configured Azure Blob Storage account/container with run-folder organization

When inference mode is not enabled, normal application behavior remains unchanged.

## Goals

- Author ground truth cases with:
  - an input record
  - a sequence of user prompts
  - an expected output record
- Run inference for the full ground truth list.
- Support repeated full-list inference runs.
- Capture structured run artifacts with timing and execution details.
- Support deterministic search plug-in behavior from app-root config.

## Ground Truth Storage

Ground truth assets are stored under the repository root folder `ground-truth/`.

- Case files are JSON only.
- Prompt sequences are stored as exact literal strings and replayed exactly as authored.
- Expected output records are stored in each ground truth JSON file.
- Ground truth is grouped into subfolders so different case sets can use different schemas and project settings.
- `ground-truth/config/` is the app-root config folder for inference-wide settings and local tool plug-ins.
- Each direct subfolder under `ground-truth/`, except `config/`, is one inference project.
- Each group must include `config/schema.json`.
- Each group may include `config/prompt.md` and `config/config.json`.
- The run input set is all JSON files found directly in each group folder, excluding `config/` and nested files.

Suggested initial layout:

```text
ground-truth/
  config/
    search-plugin.mjs
  00/
    config/
      schema.json
      prompt.md
      config.json
    q00.json
    q01.json
  01/
    config/
      schema.json
    q00.json
```

## Inference Output Storage

Inference output artifacts must be pushed to Azure Blob Storage.

- Outputs are organized by run in blob paths.
- Outputs include run-folder organization so multiple runs can be grouped under one evaluation campaign.
- Inference output reuses the application Azure storage configuration (`AZURE_STORAGE_ACCOUNT_CONNSTRING` or `AZURE_STORAGE_ACCOUNT_NAME` with DefaultAzureCredential), and `INFERENCE_CONTAINER` selects the output container.
- Per-case result artifacts and a run manifest are uploaded for each run.
- Local filesystem output organization is not required by this spec.

## Non-goals

- No automatic grading or pass/fail logic in v0.11.0.
- No integration with external evaluation dashboards or services.

## Functional Overview

Inference runs will work like this:

1. Enumerate all direct group folders in `ground-truth/`, load each group config, and enumerate direct case JSON files in each group.
2. For each case, initialize agent context with the case input record.
3. Replay the case prompt sequence in order.
4. Route tool invocations through normal local tool plug-ins and built-in tools.
5. Capture all relevant execution signals and produce one structured output artifact per case.
6. Upload per-case artifacts and a run manifest to Azure Blob Storage under a run-organized path.

## Run Organization Model

Each inference run creates one output folder that groups the full ground truth pass.

- Each ground truth case has its own unique `ref`.
- `ref` is the stable ground truth case reference.
- The same case `ref` must be reused across runs when the case is conceptually the same.
- `runFolder` is the epoch timestamp generated for each full-list execution pass.
- `ITERATIONS` controls how many repeated full-list passes run under the generated epoch folder.
- `iteration` is the zero-based inference pass label used in per-case artifact file names.
- Every run reprocesses all JSON files in `ground-truth/`.
- Run behavior must remain deterministic for unchanged inputs and fixtures.

Example lifecycle for one run:

1. Enumerate all direct group folders in `ground-truth/`, load each group config, then iterate direct JSON files in each group as cases.
2. Start run timer and create `runFolder`.
3. Replay each prompt string in `prompts` exactly.
4. Execute in-built tools normally.
5. Load group `config/mcp.json` through the normal MCP config path when present.
6. Serve deterministic search results through the configured app-root search plug-in.
7. Upload `<case-ref>-<iteration>.json` to blob storage under the current run folder.
8. Upload `manifest.json` to blob storage under the current run folder.

## Ground Truth Data Contract

Each case should include the following fields:

- `ref`: unique stable reference for this ground truth case.
- `caseId`: derived from the source JSON filename for traceability.
- `description`: short human-readable intent of the case.
- `input`: canonical input payload provided to the agent.
- `prompts`: ordered array of exact user prompt strings for this case.
- `output`: expected target output record for later evaluation.
- `tags`: optional labels (`happy-path`, `edge-case`, `schema-validation`, etc.).

## Inference Output Contract

Each written case run artifact should include:

- `ground_truth`: unmodified source ground truth JSON.
- `inference`: all runtime evidence needed to evaluate the inference, including:
  - `ref`: unique stable ground truth reference for the source case.
  - `run_folder`: epoch identifier for this full-list run folder.
  - `iteration`: zero-based inference pass label used in the artifact file name.
  - `case_id`: source case identifier.
  - `started_at` and `finished_at` (ISO 8601 timestamps).
  - `elapsed_ms`: total case runtime.
  - `output`: final produced output record.
  - `transcript`: single ordered runtime stream sorted by entry `started_at`, containing user prompts, assistant responses, tool calls, retrieval details, and events.
    - each entry includes `type`, `started_at`, `finished_at`, `elapsed_ms`, and `success`.
    - tool-call entries include tool name, input, result or error, and timing metadata.
    - event entries include event metadata and optional errors.
  - `status` and optional `error`.
- `status`: `completed`, `failed`, or `timeout`.
- `error`: structured error payload when status is not `completed`.

Run-level manifest should include:

- `runFolder`
- `iterations`
- ground truth metadata, including case refs
- case counts by status
- aggregate timing (`totalElapsedMs`, `avgCaseElapsedMs`)
- list of artifact blob paths

Blob output paths should include run context, for example:

- `<runFolder>/manifest.json`
- `<runFolder>/<case-ref>-<iteration>.json`

## Deterministic Tooling Requirement

During inference harness execution:

- In-built tools must remain available and unchanged.
- group `config/mcp.json` follows the normal project config behavior.
- one deterministic search plug-in must be available for evaluation from `ground-truth/config`.
- the deterministic search plug-in description must appear production-like and must not disclose that it is fake.
- Tool requests must be routed through the normal local tool plug-in runtime.
- Deterministic search behavior must be reproducible for the same in-memory plugin data and inputs.

This preserves focus on agent behavior while removing external system variance.

## Execution Modes

v0.11.0 should support:

- Whole-run inference for the entire ground truth list.
- Global timeout of 10 minutes per ground truth run.
- `ITERATIONS` control for repeated full-list runs.

## Validation Policy

v0.11.0 does not require schema validation for ground truth files.

- Loader behavior can assume trusted input for this version.
- Parsing errors should still return structured run errors.

## Observability Expectations

Inference should emit stable, structured telemetry aligned with existing project conventions:

- include `runFolder` and `caseId` correlation on all run events
- include `elapsedMs` for case and tool call operations
- avoid logging secrets or full sensitive payloads

## Acceptance Criteria

v0.11.0 is complete when:

- We can author and load all ground truth JSON files with the required fields.
- We can run deterministic inference for the entire ground truth list.
- We can execute multiple runs over the same ground truth list with distinct run folders.
- Ground-truth group `config/` settings are honored during harness runs.
- Structured case artifacts and run manifest are uploaded to Azure Blob Storage.
- Artifacts contain sufficient data for future evaluation pipeline work.

## Out of Scope Follow-up (Planned Next)

Future versions will add:

- scoring and metric computation
- pass/fail thresholds
- report generation and trend analysis

## Decisions Finalized

- Ground truth format is JSON only.
- Ground truth root folder is `ground-truth/` containing only case JSON files (no extra structure).
- In-built tools remain unchanged.
- A deterministic search plug-in is available during inference, with a normal production-like tool description.
- Global timeout is 10 minutes per ground truth run.
- Schema validation is out of scope for v0.11.0.
- User prompts are exact strings authored directly in ground truth cases.
- Inference always runs over the entire ground truth list.
- Inference output artifacts are uploaded to Azure Blob Storage and organized by run.
- Iteration metadata is present in artifacts and blob path organization.
- `ref` is the stable ground truth case reference and is unique per ground truth file.
