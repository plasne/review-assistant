## Product Goal

Enable Review Assistant to move from feedback-only review into guarded record curation: users and agents can stage record edits, create new records, enrich records with external search context, update project schemas, and use richer project-specific chat context without losing unsaved work or leaking storage details into the renderer.

## Delta From v0.5.0

v0.5.0 added feedback configuration, user attribution, feedback storage, and feedback history. v0.6.0 captures the app behavior now implemented around record authoring, agent-assisted record updates, richer display configuration, external MCP servers, chat attachments, and in-app GitHub Copilot login.

Newly in scope:

- Draft-based record editing with explicit save and discard boundaries.
- New record creation from the UI as an unsaved draft.
- Inline editing for fields configured with `editMode: "inline"`.
- Unsaved-change protection across project, record, refresh, create, close, and active-agent navigation.
- Project `_config.json` presentation configuration for chat transcript and evidence-oriented record fields.
- App-level and project-level Markdown prompts loaded from `_prompt.md`.
- Text-file chat attachments.
- In-app GitHub Copilot device-code login.
- App-level and project-level external MCP server configuration through `_mcp.json`.
- Expanded local tools for schema inspection, schema saving, turn authoring, and search-result persistence.
- GitHub Copilot SDK session hardening, permission gating, and temporary workspace cleanup.

Still out of scope:

- Persisted chat history.
- Multi-provider runtime selection UI.
- Tool approval UI for every individual tool call.
- Real-time collaborative editing or automatic merge conflict resolution.
- Installer packaging, auto-update, or remote telemetry pipelines.

## Functional Requirements

### Record Drafts and Save Boundary

- Record changes must be staged in an in-memory draft store before they are written to the backing storage adapter.
- Draft state must be keyed by trusted project and record identifiers.
- The UI must expose whether the selected record has unsaved changes and enable record saving only when unsaved changes exist.
- Saving a draft must write the staged record to storage and clear the draft state for that record.
- Discarding a draft must clear staged changes without modifying persisted storage.
- If no draft exists for an existing record, save must return the current persisted record without changing storage.
- Feedback submissions and logged edits must participate in the same draft lifecycle as inline record edits.
- Agent tool updates must write through the draft-aware storage adapter so agent-authored changes are staged until the user saves.

### Draft Conflict Protection

- Saving a draft must fail if the persisted record changed after the draft was staged.
- New-record saves must fail if a persisted record with the same id appears before save.
- Existing-record saves must compare against the staged base data or backend concurrency marker before overwriting persisted storage.
- Conflict failures must preserve the draft and show an actionable message telling the user to refresh, review latest changes, and stage edits again.
- Local and Azure storage adapters must enforce the same conflict semantics.

### New Record Creation

- The record list must include a create-record action when a project is selected.
- New records must be created as unsaved drafts initialized with an empty object.
- The new record must appear in the record list immediately and become the selected record.
- The `.json` extension must be optional in the filename dialog.
- Record filenames must be non-empty, must not start with `_`, must not contain path separators or `..`, and must use only letters, numbers, dots, underscores, and hyphens.
- Duplicate persisted filenames must be rejected in the create-record dialog before calling storage.
- Discarding a draft-only record must remove it from the record list.
- Draft-only records must remain visible and selected across project refreshes triggered by agent completion.

### Inline Record Editing

- Fields configured with feedback `editMode: "inline"` must render editable controls in the record detail view.
- Primitive strings and raw JSON fields must be editable inline.
- Enum fields must render a select control with available enum values and a not-set state when the value is undefined.
- Inline edits must update the selected record draft and re-render validation results against the changed data.
- Inline edit updates must be serialized so slower earlier responses cannot overwrite newer draft data.
- Inline editing must preserve existing feedback properties while updating core record data.

### Unsaved-Change Navigation Guard

- The app must warn before leaving a selected record with unsaved staged changes or pending feedback drafts.
- Guarded actions include switching projects, switching records, refreshing records, creating projects, creating records, and closing the window.
- The warning dialog must allow users to stay, discard changes, or save and continue.
- When a chat response is streaming, guarded navigation must be blocked with a message that the agent may still stage record changes.
- The Electron window close event must route through the renderer guard before allowing the main window to close.
- Browser unload must also be prevented while unsaved changes exist.

### Display Presentation Configuration

- Projects may define presentation settings in `_config.json` to customize record rendering without changing record data.
- `_config.json` must support a `properties` object keyed by JSON Pointer paths.
- Display entries must support these presentations:
  - `chat-request`
  - `chat-response`
  - `evidence-list`
- Display paths may use `*` to match array item indexes.
- Invalid display entries must be ignored rather than breaking project open.
- `chat-request` and `chat-response` fields must render as collapsible presentation fields.
- `evidence-list` arrays must render as evidence-oriented cards.
- Users must be able to toggle visibility of fields that exist in record data but are not declared in the schema.

### Prompt Context

- App-level `_prompt.md` beside the app `.env` must be loaded when present.
- Project-level `_prompt.md` inside the selected project must be loaded when present.
- Chat system prompt context must combine app-level and project-level prompts, with project prompt content included after app prompt content.
- Prompt loading must support both local filesystem and Azure Blob projects.
- Prompt content must be assembled in main process code, not renderer code.

### Chat Attachments

- Users must be able to attach text files to the next chat request.
- Attachment selection must be owned by the main process through an Electron file dialog.
- Attachments must be limited to at most five files.
- Each attachment must be a file, must be under 64 KB, must not contain NUL bytes, and must decode as valid UTF-8 text.
- Allowed file filters must target text and source formats such as Markdown, JSON, YAML, CSV/TSV, logs, XML/HTML/CSS, JavaScript/TypeScript, Python, Java, C#, Go, Rust, Ruby, PHP, shell, and SQL.
- The renderer must show selected attachment chips with filename and formatted size.
- Removing an attachment chip must discard the cached attachment content in main.
- Sending a chat must pass cached attachment content to the provider and clear the cache after resolution.
- If a message is empty but attachments are present, the app must send a default instruction asking Copilot to review the attached files.
- Displayed user chat messages must include an attachment summary while provider requests receive the original message text plus attachment content.

### In-App GitHub Copilot Login

- The chat UI must expose a GitHub login action.
- When Copilot auth is required, the unavailable-agent panel must show a `Continue with GitHub` action.
- Starting login must invoke the main-process GitHub Copilot login flow.
- Device-code login must show a modal with the verification URI and device code.
- The device code must be copied to the clipboard when available and the UI must disclose that it was copied.
- Login completion events must refresh agent availability on success.
- Login failures must surface a user-visible error message.
- Login events must be correlated by `loginId` so stale completion events do not close the wrong dialog.

### External MCP Server Configuration

- The app must load optional `_mcp.json` files from both app-level and project-level locations.
- `_mcp.json` must contain an `mcpServers` object.
- Each MCP server entry must define an id, command, optional args, optional env, optional timeout, and optional allowedTools.
- MCP server ids must contain only letters, numbers, underscores, or hyphens.
- `args` and `allowedTools` must be string arrays.
- `timeout` must be a positive integer when present.
- Environment values in `_mcp.json` may reference `${NAME}` placeholders resolved from app/project configuration or process environment.
- Missing environment references must fail clearly before chat starts.
- Project-level MCP servers must override app-level servers with the same id while preserving unrelated app-level servers.
- External MCP servers must be passed to GitHub Copilot as stdio MCP servers.
- External MCP permissions must allow only configured servers and configured tools; unregistered server/tool permission requests must be rejected.

### Expanded Local Tools

- The built-in local tool list must include:
  - `readRecord`
  - `getRecordSchema`
  - `discoverCanonicalSchemaMappings`
  - `saveGeneratedSchema`
  - `saveSearchResults`
  - `startTurn`
  - `completeTurn`
  - `listTools`
- All tools must use trusted UI-selected project and record context rather than accepting project or record ids from tool arguments.
- Tool responses must round-trip `requestId` and return stable `AgentErrorEnvelope` failures.
- Tool writes must route through the draft-aware storage adapter when a project is selected.
- Tool responses must not expose credentials, raw filesystem paths, Azure container internals, or feedback properties.

### Schema Authoring Tools

- `getRecordSchema` must return the selected record schema, optionally at a JSON Pointer.
- `getRecordSchema` must optionally return schema-derived turn destination candidates.
- `saveGeneratedSchema` must save a generated JSON Schema as the selected project `_schema.json`.
- Saving a generated schema must validate that the schema is a JSON Schema object before replacing the current schema.
- Existing schemas must be backed up to `_schema_1.json`, `_schema_2.json`, and so on, filling the first available backup number.
- Schema save failures must leave the existing `_schema.json` unchanged.
- Feedback configuration must be normalized after schema changes so stale targets are removed and new schema fields receive defaults.

### Agent-Assisted Record Authoring Tools

- `discoverCanonicalSchemaMappings` must return canonical schema mapping candidates for the selected record schema.
- `saveSearchResults` must append or replace entries in an array container of the selected record draft.
- `saveSearchResults` must validate only the destination container against its schema before staging the change.
- `startTurn` must create or update a conversation turn from a user inquiry and optional already-known response.
- `startTurn` must infer likely turn destinations and fields when unambiguous, and require `targetPath` or `fieldMapping` when ambiguous.
- `completeTurn` must complete an existing turn by setting the final response and optional evidence in one staged update.
- Turn tools must support explicit field mappings for schemas that do not use common inquiry, response, or evidence field names.
- Turn and search-result tools must reject invalid JSON Pointers, incompatible schemas, invalid result shapes, and ambiguous targets with clear messages.

### GitHub Copilot SDK Session Behavior

- GitHub Copilot chat must use the Copilot SDK runtime with streaming enabled.
- Each provider status or chat run must use an isolated temporary working directory.
- Temporary working directories must be cleaned after status checks, completion, cancellation, or failures.
- Chat sessions must disable ambient config discovery, custom instructions, remote custom agents, scheduling, canvas rendering, MCP apps, large output, and infinite sessions unless explicitly added in a later requirement.
- Local tools must be exposed as Copilot custom tools.
- External MCP tools must be exposed through Copilot MCP server configuration.
- Available tools must include registered local tools and all configured MCP tools.
- Local tool permission requests for registered tools may be approved once; unregistered custom tools must be rejected.
- Cancellation must abort the active Copilot SDK session and release runtime resources.

## Architecture Requirements

- Renderer remains UI-only and must not access filesystem, Azure Blob Storage, child processes, Copilot transport, or MCP transport directly.
- Preload must expose only typed, allowlisted IPC methods and event subscriptions.
- Main process owns configuration loading, prompt loading, attachment reading, storage access, draft orchestration, external MCP parsing, login flow, and chat request assembly.
- Agent worker/provider code owns GitHub Copilot SDK transport details.
- Storage backends must stay behind `StorageAdapter`.
- Draft-aware storage must be provided as an adapter wrapper rather than leaking draft logic into renderer code.
- Local and Azure storage adapters must support the same public record, schema, prompt, MCP, display, feedback, and draft persistence semantics where backend capabilities permit.

## Observability Requirements

- Chat start logging must include project id or `none`, record id or `none`, message character count, history count and character count, attachment count and character count, system prompt source, system prompt character count, local tool count, local tool names, external MCP server ids, and context assembly duration.
- Auth logging must include login started, device code ready, and login completed events with provider and login correlation fields.
- Provider logging must include Copilot SDK session spawn, cancellation failures, disconnect failures, stop failures, and elapsed durations where applicable.
- Tool execution logging from prior requirements must continue to avoid full record payloads.
- Logs must continue to redact secrets and avoid full attachment contents.

## Test and Harness Requirements

- Unit tests must cover:
  - Draft staging, save, discard, new-record creation, and conflict preservation.
  - `_config.json` presentation normalization and wildcard path matching.
  - `_mcp.json` parsing, environment expansion, validation failures, and app/project merge behavior.
  - Chat attachment validators and limits.
  - Expanded local tool argument validation and draft-aware write behavior.
  - Copilot SDK provider tool exposure, MCP mapping, permission handling, and cancellation cleanup.
- Integration tests must cover:
  - Local storage display config loading.
  - Project-level prompt loading from `_prompt.md`.
  - Project-level config and MCP loading with backend-key override protection.
  - Schema save backup rotation and invalid-schema rollback.
  - Feedback config normalization after schema changes.
  - Local and Azure draft write conflict behavior where deterministic adapters are available.
- UI tests must cover:
  - Chat attachments shown, removed, sent, and cleared.
  - New record creation as an unsaved selected draft.
  - Inline edit staging, validation refresh, enum editing, and serialized updates.
  - Unsaved-change warning for close, project switch, record switch, refresh, create project, and create record.
  - Active-agent navigation blocking.
  - Display presentations for chat request, chat response, and evidence list fields.
  - GitHub login modal and completion behavior.
- E2E and smoke tests must cover:
  - Preload/main IPC pairing for record draft, attachment, login, close-guard, and chat stream channels.
  - Electron security settings remain enabled.
  - A real Electron flow where a record can be created, edited, saved, and reloaded.
  - A chat/tool flow where agent-authored record changes are staged and protected by the save boundary.
- Required deterministic gates remain:
  - `npm run lint`
  - `npm run typecheck`
  - `npm run test:unit`
  - `npm run test:integration`
  - `npm run test:ui`
  - `npm run test:e2e`
  - `npm run smoke`
  - `make audit-harness`

## Acceptance Criteria

v0.6.0 is complete when:

- Users can create a new record draft, edit schema-configured fields inline, and save or discard the draft explicitly.
- Existing record edits, feedback submissions, logged edits, and agent tool writes are staged until save.
- The app prevents accidental loss of unsaved work across navigation and close flows.
- Conflicting persisted changes block save without destroying the staged draft.
- Projects can customize record presentation with `_config.json`.
- Chat can include app/project `_prompt.md` context and validated text-file attachments.
- Users can complete GitHub Copilot device-code login inside the app.
- App/project `_mcp.json` files can add external MCP servers with environment expansion and permission gating.
- Expanded local tools can inspect schemas, save generated schemas, persist search results, and author conversation turns through trusted UI context.
- Renderer remains free of filesystem, Azure, MCP, Copilot transport, and draft persistence ownership.
- Deterministic harness commands pass with behavior-focused coverage for the v0.6.0 surfaces.
