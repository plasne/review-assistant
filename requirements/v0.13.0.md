# v0.13.0 - Distribution

## Overview

v0.13.0 adds Azure Storage Queue integration for distributing work across Review Assistant instances. Users create named queues, push filtered records into them with custom instructions, and consume records one at a time from queue messages. The feature includes an exclusive blob lease system to prevent concurrent edits and record change tracking for audit purposes.

**Scope**: Queue creation, message publishing, queue consumption, record history tracking, and lease-based concurrency control.

**Out of Scope**: User/role-based queue access control, dead-letter queue handling, queue analytics/metrics, message scheduling, or batch queue consumption.

---

## Exclusive Lease

An exclusive lease is a time-bounded lock on a record blob in Azure Blob Storage that prevents concurrent edits. The system automatically manages lease acquisition, renewal, and release.

### Current Implementation

- **Storage**: Azure Blob Storage leases on `{project-id}/{record-id}.json` blobs
- **Local adapter**: Leases are unsupported (`NOT_SUPPORTED` status)
- **Lease duration**: 60 seconds per lease
- **Auto-renewal interval**: Every 30 seconds (keeps lease fresh until released)
- **Lifecycle**:
  1. When a record is opened (user clicks to view), `obtainExclusiveLease(projectId, recordId)` is called
  2. Lease acquired successfully returns `{ status: 'SUCCESS' }`
  3. Lease already held by another client returns `{ status: 'FAILURE' }` (prevent opening)
  4. If record does not exist, throws error
  5. Lease is auto-renewed every 30s while record remains open
  6. When user leaves the record (switches project or closes app), lease is released via `releaseExclusiveLease(projectId, recordId)`

### Lease Interaction with Queues

For records consumed from a queue:

- **On pull**: User obtains exclusive lease on the record (follows normal open-record flow)
- **On save**: User saves record data; if record was queue-sourced, the queue message is marked complete (deleted from queue)
- **On leave without save**: User navigates away; lease is released, message becomes visible again with default visibility timeout (~30s)

### Conflict Handling

- If a user tries to open a record that is already leased, the UI shows a conflict error: `"Record is being edited by another user. Try again in a moment."`
- The client may retry lease acquisition with exponential backoff
- Stale leases (network partition) expire after 60 seconds and are auto-released by Azure

## Record History

Records now track a change history to support audit logging and distribution workflows.

### Record Change Tracking

Each record blob includes an optional `_history` field containing a list of changes:

```json
{
  "answer": "...",
  "tags": [...],
  "_history": [
    {
      "username": "alice@example.com",
      "timestamp": "2026-06-11T14:30:00Z",
      "action": "saved"
    },
    {
      "username": "bob@example.com",
      "timestamp": "2026-06-11T14:25:00Z",
      "action": "saved"
    }
  ]
}
```

### History Field Specification

- **Field name**: `_history` (underscore-prefixed, not rendered in record UI)
- **Type**: Array of `HistoryEntry` objects
- **Order**: Most recent entry last (append-only)
- **Persistence**: Appended when record is saved; persists across edits
- **Reading**: When loading a record, `_history` is preserved but not edited by the record edit UI
- **Structure of `HistoryEntry`**:
  - `username` (string): Username from project configuration (`USERNAME` env var)
  - `timestamp` (string): ISO 8601 UTC timestamp of save
  - `action` (string): One of `"saved"` or `"reviewed"` (mutually exclusive per save)
    - `"saved"`: Record was edited directly by user (not from queue)
    - `"reviewed"`: Record was pulled from queue, reviewed, and saved by user

### Changes from v0.12.0

- Records now accumulate history; existing records without `_history` are treated as having empty history
- Saving a record appends a new history entry
- History is not user-editable; generated automatically by the save operation

## Create Queues

Users create work queues and enqueue records by filtering projects by tags and adding records with custom instructions.

### Queue Lifecycle

#### Create Queue

- **UI trigger**: Button in top navigation bar (labeled "Queues" or similar)
- **Modal**: Displays existing queues with message counts and queue management options
- **Create action**: User clicks "Create Queue", prompted for queue name
- **Validation**: Queue names must match `^[a-z0-9-]{1,63}$` (lowercase alphanumeric and hyphens, 1-63 chars)
- **Creation**: Calls `createQueue(queueName)` in main process, which creates an Azure Queue with the given name
- **Success**: Queue appears in modal list with count 0; user can begin adding messages

#### Add Records to Queue

**Workflow**:

1. User selects a queue from the modal
2. User selects a project from a project dropdown
3. User configures tag filters (see Tag Filtering below)
4. User clicks "Search" → system queries and displays matching records
5. User chooses "Add All" or "Add Sample" (specifying a number)
6. User optionally enters instructions (text field, ~200 chars suggested)
7. User clicks "Add to Queue"
8. For each selected record:
   - Create queue message: `{ project, filename, instructions }`
   - Call `enqueueMessage(queueName, message)`
   - Azure Queue stores message with default visibility timeout (~30s in dev, production depends on config)

**Message Deduplication**: The system does not prevent adding the same record to a queue multiple times. If a user searches and adds records, then searches again and adds the same records, they will be enqueued again.

**Sample Size**: No upper limit enforced; if user specifies sample size > number of matching records, all matching records are added.

**Instructions Field**: Optional free text (no special validation); stored as-is in queue message; displayed to user when consuming.

#### Tag Filtering

Tags are displayed as a filterable list with three states per tag:

- **Unchecked** (default): No filtering on this tag; records with or without this tag match
- **Checked** (✓): Include records tagged with this tag (OR across multiple checked tags)
- **Excluded** (✗): Exclude records tagged with this tag (AND NOT)

**Filtering Algorithm**:

```
matching_records = all records in project

for each tag_name:
  if tag is checked (inclusion):
    matching_records = matching_records ∩ records_with_tag(tag_name)

for each tag_name:
  if tag is excluded (exclusion):
    matching_records = matching_records - records_with_tag(tag_name)

return matching_records
```

**Interpretation**:

- No tags selected: return all records
- Checked tags (e.g., "domain:legal", "domain:finance"): return records with at least one checked tag (OR logic)
- Excluded tags (e.g., "turns:multi" with ✗): remove records with excluded tags (NOT logic)
- Mix: inclusion first, then exclusion

**Tag Source**: Loaded from project's tag definitions (`getTagDefinitions(projectId)`).

#### Queue Management

From the modal, user can:

- **Refresh queue list**: Click "Refresh" to reload queue names and message counts
- **Clear queue**: Select queue, click "Clear" → confirms, then removes all messages from queue (via `clearQueue(queueName)`)
- **Delete queue**: Select queue, click "Delete" → confirms, then deletes queue (via `deleteQueue(queueName)`)

## Read from Queues

Users consume one record at a time from a queue by selecting the queue and fetching the next message.

### Queue Consumption Workflow

**Availability**: Feature only available if backend is Azure (not LOCAL_PATH) and at least one queue exists.

**UI Location**: Top navigation bar with queue selector and "Get Record" button.

#### Steps

1. User selects a queue from dropdown (populated by `listQueues()`)
2. User clicks "Get Record from Queue"
3. System calls `dequeueMessage(queueName)`:
   - Returns `{ message, popReceipt }` if available
   - Throws error if queue is empty or does not exist
4. **If message received**:
   - Parse `{ project, filename, instructions }`
   - Open project via `openProject(project)`
   - Load record via `getRecord(project, filename)`
   - Obtain exclusive lease via `obtainExclusiveLease(project, filename)`
   - Switch UI to project/record view
   - Display instructions as a message banner (similar to error/warning style)
   - Store `popReceipt` in memory for later completion (see below)
5. **If no message** (queue empty or error):
   - Display message: `"No messages in queue."`
   - Do not change current record/project

#### Message Completion

When a user **saves** a record that was consumed from a queue:

- Call `completeMessage(queueName, popReceipt)` to delete the message from the queue
- Append history entry with action `"reviewed"` (instead of `"saved"`)
- Clear stored `popReceipt` so leaving the record does not attempt re-completion

When a user **leaves** a record without saving (switches project, closes app, etc.):

- If `popReceipt` is stored and visibility timeout has not expired, the message becomes visible again in queue automatically (via Azure's timeout mechanism)
- Do not call `completeMessage`; allow message to re-appear

### Message Visibility Timeout

Azure Queue default visibility timeout is approximately 30 seconds. After dequeuing, if no `completeMessage` is called within this window, the message becomes visible and can be dequeued again. This allows work to be re-distributed if a session crashes or user abandons the record.

## Data Structures

### Queue Message

```typescript
type QueueMessage = {
  project: string; // Project ID (alphanumeric, dashes)
  filename: string; // Record ID, no .json suffix (alphanumeric, dashes, underscores)
  instructions?: string; // Optional user-provided instructions
};
```

### Queue Metadata

```typescript
type QueueInfo = {
  name: string; // Queue name
  messageCount: number; // Approximate count of visible messages
};
```

### Dequeue Result

```typescript
type DequeueResult = {
  message: QueueMessage;
  popReceipt: string; // Opaque token to complete/delete message
};
```

### History Entry

```typescript
type HistoryEntry = {
  username: string;
  timestamp: string; // ISO 8601
  action: "saved" | "reviewed";
};
```

## API Contract

### Storage Adapter Methods

New methods added to `StorageAdapter` interface (Azure-only; local adapter throws `NOT_SUPPORTED` or no-op):

```typescript
// Queue Management
listQueues(): Promise<QueueInfo[]>;
createQueue(queueName: string): Promise<QueueInfo>;
deleteQueue(queueName: string): Promise<void>;
clearQueue(queueName: string): Promise<void>;

// Queue Operations
enqueueMessage(queueName: string, message: QueueMessage): Promise<void>;
dequeueMessage(queueName: string): Promise<DequeueResult | null>; // null if empty
completeMessage(queueName: string, popReceipt: string): Promise<void>;

// Search (used by tag filtering)
searchRecords(projectId: string, tagFilter: TagFilter): Promise<RecordSummary[]>;
```

### Tag Filter Structure

```typescript
type TagFilter = {
  included: string[]; // Tag names to include (OR)
  excluded: string[]; // Tag names to exclude (AND NOT)
};
```

**Implementation note**: `searchRecords` filters records in project by iterating records and checking tags against the filter; it does not require a separate search index.

### Preload API Extensions

New IPC channels (from renderer to main):

```typescript
reviewAssistant.queue.listQueues(): Promise<QueueInfo[]>;
reviewAssistant.queue.createQueue(queueName: string): Promise<QueueInfo>;
reviewAssistant.queue.deleteQueue(queueName: string): Promise<void>;

  projectId: string,
  tagFilter: TagFilter
): Promise<RecordSummary[]>;

  queueName: string,
  message: QueueMessage
): Promise<void>;
reviewAssistant.queue.dequeueMessage(
  queueName: string
): Promise<DequeueResult | null>;
```

**Trigger**: "Queues" button in top navigation bar (visible only if Azure backend detected).

**Layout**:

When a record is loaded from queue:

- Display banner at top of record view
- Style: info/neutral color (not error)

## Error Handling

### Common Errors

| Scenario                     | Error                        | UI Feedback                                                                         | User Action                                               |
| ---------------------------- | ---------------------------- | ----------------------------------------------------------------------------------- | --------------------------------------------------------- |
| Queue name invalid           | Validation error             | "Queue name must contain only lowercase letters, numbers, and hyphens (1-63 chars)" | Correct input, retry                                      |
| Queue already exists         | 409 Conflict                 | "Queue '{name}' already exists"                                                     | Choose different name or use existing queue               |
| Queue not found              | 404 Not Found                | "Queue '{name}' not found"                                                          | Refresh queue list, try another queue                     |
| No messages in queue         | Empty queue                  | "No messages in queue"                                                              | Choose different queue or create/populate new queue       |
| Message dequeue timeout      | Network/timeout              | "Failed to retrieve message. Check your connection and try again."                  | Retry after a moment                                      |
| Lease conflict               | Lease held by another client | "Record is being edited by another user. Try again in a moment."                    | Wait or retry                                             |
| Project not found            | 404                          | "Project '{project}' not found. It may have been deleted."                          | Go back, refresh, or choose different queue               |
| Record not found             | 404                          | "Record '{filename}' not found in project '{project}'. It may have been deleted."   | Go back, clear queue message manually, try another record |
| Local storage backend active | Not supported                | "Queues are only available with Azure Blob Storage backend"                         | No action (feature unavailable)                           |
| No queues exist              | Empty list                   | "No queues available. Create a queue to get started."                               | Open Queue Manager, create queue                          |

### Retry Logic

- Network timeouts: Implement exponential backoff (e.g., 100ms → 200ms → 400ms, max 3 retries)
- Lease conflicts: Retry lease acquisition up to 3 times with 1-2s delays
- Queue empty: No automatic retry; show message and allow manual retry

## Local Adapter Behavior

The `LocalStorageAdapter` does not implement queue functionality. All queue methods:

- Throw `NotSupportedError` with message `"Queues are only available with Azure Blob Storage backend"`, or
- Return empty/no-op results (e.g., `listQueues()` returns `[]`)

The decision is consistent with the existing pattern: local storage provides file-system-based project review; queues require distributed task coordination not suitable for local filesystem.

## Architecture Notes

- **Queue storage**: Azure Storage Queue (not Blob Storage)
- **Message format**: JSON, stored as queue message text payload
- **Lease scope**: Individual record blobs, not queues
- **History scope**: Individual record blobs, appended on save
- **Concurrency**: Exclusive leases prevent concurrent editing; queue messages auto-redistribute on timeout
- **Audit trail**: Combined lease tracking + history field provides who/when/action visibility
