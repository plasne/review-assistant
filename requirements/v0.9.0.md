## Summary

This release introduces tag support with:

- Computed tags produced by plugins at save time
- Manual tags defined in JSON files and managed by users
- Tag assets loaded from app-level and project-level tags folders
- Schema-scoped computed tag plugins that can mutate records directly
- A dedicated tags presentation for arrays of strings

## Scope

### In scope

- Tags persisted as an array of strings
- Synchronous plugin execution during record save
- Plugin discovery from app-level and project-level tags folders
- Schema-specific computed tag plugin execution
- Direct record mutation by computed tag plugins
- Manual tag add and remove in UI when edit mode permits edits
- Manual tag definitions loaded from tags/manual.json
- Aggregate plugin failure reporting without blocking save

### Out of scope

- Tags persisted as arrays of objects
- Tag-based API filtering and query behavior
- Permission rules that restrict which tags can be applied

## Data model

### Record storage

- A tags field is a string array.
- Maximum tags per record is 100.
- Maximum length per tag is 100 characters.
- Tag names are the identity. There is no separate tag id.

### Tag definitions

- Tag definitions are supplied by JSON metadata files, not by plugins.
- Manual tag definition files are discovered at:
  - app-level tags/manual.json
  - project-level tags/manual.json
- A definition contains:
  - name
  - description
- Definitions are merged using deterministic load order: project-level first, then app-level.
- If multiple files define the same name, the first definition wins and later conflicting definitions are ignored.

## Plugin model

### Discovery and location

- Computed tag plugins are discovered from tags folders at:
  - app-level tags
  - project-level tags
- Manual tags are not provided by plugins.
- Manual tag metadata must come from tags/manual.json.

### Schema-specific plugin binding

- Each computed tag plugin targets a specific schema.
- A plugin must only run for records whose schema matches the plugin target.
- Plugins that do not match the active schema must be skipped.

### Computed tag contract

For a given record, a computed-tag plugin receives a mutable record object and may directly mutate the record, including:

- Reading schema-specific fields needed for computed tag decisions
- Writing tags to the schema-specific tags field path
- Updating plugin-owned tags in place on the record object

Plugins are responsible for deterministic mutation output for the same input record.

## Save-time execution and reconciliation

### Execution model

- Computed tag plugins run synchronously on record save.
- Plugins run independently. A failure in one plugin does not stop other plugins.
- Record save proceeds even if one or more plugins fail.
- Plugin execution order must be deterministic for a given schema.

### Reconciliation algorithm

For each applicable schema-specific plugin:

1. Provide the current record object as mutable input.
2. Allow the plugin to mutate tag-related content directly on the record.
3. Validate final tag constraints before persistence.

Additional rules:

- Computed tags are not user-modifiable.
- Manual tags are user-modifiable when edit mode allows edits.
- Deduplicate tag names in the final persisted array.
- Preserve stable ordering where practical, while guaranteeing deterministic output.

### Failure handling

- Aggregate plugin failures into a single user-visible alert per save.
- The alert must indicate that save succeeded but one or more tag plugins failed.
- Unit tests must cover framework behavior and partial failure cases, and verify:
  - other plugins still run
  - save still succeeds
  - aggregate error is surfaced

### Testing boundaries

- Unit tests may validate plugin framework functionality and host/plugin contracts.
- Unit tests must not depend on or validate behavior of repository-specific production plugins.
- Test fixtures or synthetic plugins may be used to validate framework behavior.

## Presentation behavior

### Applicability

- The tags presentation is supported only for string arrays.

### UI behavior

The tags presentation must allow users to:

- View computed tags
- View manual tags
- Add and remove manual tags when editing is enabled

The tags presentation must not allow users to:

- Add or remove computed tags directly

### Edit mode behavior

edit_mode values are:

- none: read-only, no manual tag edits
- inline: direct field editing
- logged: edits captured through logged edit workflow and history

For tags, manual tag editing is allowed only when edit_mode is inline or logged.

## Acceptance criteria

1. Tags are persisted as string arrays only.
2. A record never persists more than 100 tags, and no tag exceeds 100 characters.
3. Computed plugins are discovered from app-level and project-level tags folders.
4. Manual tag definitions are loaded from tags/manual.json files with name and description fields.
5. Save continues when one or more plugins fail, and an aggregate error is shown.
6. Computed plugins are schema-specific and run only when schema matches.
7. UI separates computed tags from manual tags.
8. Computed tags are non-editable by users.
9. Manual tags are editable only when edit_mode is inline or logged.
10. Unit tests cover plugin framework behavior and aggregate failure behavior without testing production plugin implementations directly.
