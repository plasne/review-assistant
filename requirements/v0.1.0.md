## Product Goal

Build a cross-platform Electron desktop application that helps users review inference results and curate ground truth records within isolated projects.

## In Scope for v0.1.0

- Cross-platform desktop app using Electron on Windows, macOS, and Linux.
- Two data backends supported at launch.
  - Local filesystem projects.
  - Azure Blob Storage projects.
- Project-first user flow where selecting a project is the first interaction.
- Schema-driven read-only record detail view using each project's `config/schema.json`.
- Chat panel for interacting with a single local agent.
- Engineering harness with deterministic checks, behavior-focused tests, and CI gates.

## Out of Scope for v0.1.0

- Record editing and write-back to storage.
- Approval/export workflow enforcement in UI.
- Installer packaging and auto-update.
- Telemetry pipelines beyond local console logging.
- Multi-agent orchestration and chat history persistence.

## Architecture

### Runtime Model

- Use Electron with a secure multi-process architecture.
- Keep UI responsive by running agent interactions off the renderer thread.
- Recommended process split for v0.1.0.
  - Renderer process for UI only.
  - Main process for app lifecycle, storage access orchestration, and IPC routing.
  - Utility process or worker process for agent invocation and long-running tasks.

### Electron Security Defaults

Use secure defaults unless a documented exception is required:

- `contextIsolation: true`
- `sandbox: true`
- `nodeIntegration: false`
- Strict, allowlisted IPC channels with request and response validation.

## Configuration

### Configuration Sources

The app must load configuration from layered `config/.env` files:

1. App-level `config/.env` beside the running code.
2. Project-level `config/.env` inside the selected project.

### Precedence

- Project-level values override app-level values.
- Variable expansion is not required in v0.1.0.

### Backend Selection Rules

On startup, determine backend from resolved configuration:

1. If `AZURE_STORAGE_ACCOUNT_CONNSTRING` exists, use Azure Blob with connection string auth.
2. Else if `AZURE_STORAGE_ACCOUNT_NAME` exists, use Azure Blob with `DefaultAzureCredential`.
3. Else if `LOCAL_PATH` exists, use local filesystem backend.
4. Else show a configuration error and block project browsing.

### Required and Optional Environment Variables

- `AZURE_STORAGE_ACCOUNT_CONNSTRING` optional, secret.
- `AZURE_STORAGE_ACCOUNT_NAME` optional, non-secret.
- `LOCAL_PATH` optional, non-secret.

### Logging Requirements

- Log effective configuration values when loading config.
- Redact secrets in logs.
- Example: `AZURE_STORAGE_ACCOUNT_CONNSTRING=****`.
- Use console logging only for v0.1.0.

## Project Model

### Project Definition

A project is an isolation boundary for reviewing a dataset:

- Local backend: each project is a subdirectory under `LOCAL_PATH`.
- Azure backend: each project is a Blob container.

### Required Project Files

- `config/schema.json` required in every project.

### Optional Project Files

- `config/.env` project-level overrides.
- `config/prompt.md` prompt for local agent behavior. For local inference workflows, this file should exist in each project.

### Typical Record Contents

Projects may contain JSON records representing ground truth, inference, evaluation, and feedback data.

### Record Discovery

- Treat project-root `.json` files as records.
- Ignore non-JSON files and reserved configuration files under `config/`.

### Record Identity and Display

- Record identity for UI list is filename without `.json`.
- Show records by that display name.

### Project Validation Behavior

- If a user opens a project missing `config/schema.json` or with invalid configuration, show an error.
- Do not silently fall back.

## Schema and Validation

### Schema-First Contract

- Every project's `config/schema.json` defines expected record shape.
- The details panel must be generated dynamically from schema.

### Example Schema

The following example from the original requirements is retained for implementation reference:

```json
{
  "type": "object",
  "properties": {
    "id": {
      "type": "string",
      "description": "Unique identifier for the record."
    },
    "persona": {
      "type": "string",
      "description": "The persona that might ask this question.",
      "enum": ["TPM", "developer", "SME"]
    },
    "question": {
      "type": "string",
      "description": "The question that was asked."
    },
    "answer": {
      "type": "string",
      "description": "The answer that the agent gave."
    },
    "evidence": {
      "type": "array",
      "description": "The evidence that was found to support the answer.",
      "minItems": 1,
      "maxItems": 10,
      "items": {
        "type": "object",
        "properties": {
          "id": {
            "type": "string"
          },
          "source": {
            "type": "string"
          },
          "uri": {
            "type": "string"
          },
          "content": {
            "type": "string"
          }
        },
        "required": ["id", "source", "uri", "content"]
      }
    }
  },
  "required": ["question", "evidence"]
}
```

### JSON Schema Coverage

v0.1.0 must support full JSON Schema handling for read-only rendering and validation display, including complex schema constructs.

### Validation Semantics

- Records are read-only in v0.1.0.
- Validation errors should be visible in the details panel.
- Future requirement captured now: when approval workflow is added, a record that fails validation cannot be marked approved for export.

## User Interface Requirements

### Core Layout

Inside a project, render three adjustable columns:

1. Record list column.
2. Schema-driven record details column.
3. Chat column for follow-up interaction with the local agent.

### Header

- Include current project selector dropdown.
- Keep room for future controls.

### Footer

- Show app version derived from git tag and commit metadata.

### Details Panel Mode

- Read-only in v0.1.0.

### Chat Behavior

- User interacts with agent through chat window.
- Chat history is not persisted.

### Accessibility Targets

The UI should meet practical accessibility expectations in v0.1.0:

- Keyboard navigation across header and all three columns.
- Clear focus visibility and logical tab order.
- Accessible labels for interactive controls.
- Sufficient color contrast for primary text and controls.

## Agent Integration

### Local Agent Assumptions

- Assume one local agent implementation based on <https://github.com/earendil-works/pi>.
- Assume `config/prompt.md` may exist per project.

### Invocation Guidance

- Implement agent interaction behind an abstraction that keeps UI decoupled from agent runtime details.
- Prefer process-isolated invocation from main process orchestration to preserve responsiveness and fault isolation.
- Add timeout and cancellation handling for chat requests.

## Performance and Scale Targets

v0.1.0 should handle:

- Around a dozen projects.
- Single-digit thousands of records per project.
- Individual JSON records under 10 MB.

## Engineering Harness Requirements

### Harness Objective

Create a deterministic engineering harness that supports fast iteration by humans and AI coding agents.

### Required Harness Artifacts

Adopt harness practices aligned with <https://openai.com/index/harness-engineering> and the installed harness playbook skill.

Minimum artifacts and controls:

- Deterministic project commands for smoke, lint, typecheck, unit, integration, and e2e.
- CI workflow that runs all required checks.
- Architecture and observability documentation sufficient for autonomous agent execution.
- Guardrails that reduce entropy and drift in scripts and test workflows.

## Testing Requirements

### Testing Philosophy

- Prioritize behavior and outcomes over implementation details.
- Keep tests resilient to refactoring while preserving expected product behavior.

### Test Types Required

- Unit tests for core logic and schema processing.
- Integration tests for backend adapters, config loading, and IPC boundaries.
- UI tests for layout behavior, record selection, schema rendering, and accessibility basics.
- End-to-end tests for key user flows, including project selection and record review.

### CI Gates

All checks are required in CI for v0.1.0:

- Lint
- Typecheck
- Unit tests
- Integration tests
- End-to-end tests
- Smoke checks

## Versioning and Diagnostics

- Footer version source must include git tag and commit.
- Logging is console-only in v0.1.0.
- Configuration logs must redact secrets.

## Acceptance Summary

v0.1.0 is complete when the app can:

- Start from layered `config/.env` config and choose backend by the defined precedence rules.
- List projects from local or Azure Blob sources.
- Open a project and fail clearly if required files are missing.
- List record files discovered by naming rules.
- Render record details from full JSON Schema support in read-only mode.
- Provide a responsive chat pane with non-persistent session messages.
- Run deterministic harness and pass all CI-required quality gates.
