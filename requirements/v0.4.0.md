## Product Goal

Capture the functionality now implemented beyond the v0.3.0 GitHub Copilot streaming baseline: backend-neutral local tools, MCP wiring for GitHub Copilot, and regression harness coverage that proves displayed records are actually callable by the agent.

## Delta From v0.3.0

v0.3.0 required a real GitHub Copilot streaming backend and only a non-breaking foundation for future local tools. v0.4.0 promotes that follow-up tool direction into product scope.

Newly in scope:

- A backend-neutral local tool runtime owned by the main process.
- A built-in `readRecord` tool that reads the trusted UI-selected record.
- A built-in `listTools` tool that reports available Review Assistant tools.
- A GitHub Copilot MCP bridge that exposes Review Assistant local tools to the provider.
- Tool-call logging and regression tests that prove tools are callable, not merely listed.

Still out of scope:

- Third-party plugin marketplace or dynamic external tool loading.
- Tool approval UI.
- Persisted chat history.
- Multi-provider runtime selection UI.
- In-app GitHub sign-in.

## Functional Requirements

### Local Tool Runtime

- The app must define a backend-neutral `ToolInvocationRequest` and `ToolInvocationResponse` contract.
- Local tool execution must happen in the main process.
- Renderer code must not execute tools or access storage directly.
- Tool responses must round-trip `requestId` for tracing.
- Tool errors must use stable `AgentErrorEnvelope` codes.

### `readRecord` Tool

- `readRecord` must read the record currently selected in the Review Assistant UI.
- Project and record identifiers must come from trusted UI selection context, not tool arguments.
- The tool must support an optional `includeSchema` boolean argument.
- If no storage backend is available, return `BACKEND_UNAVAILABLE`.
- If no record is selected, return `NO_RECORD_SELECTED`.
- If the selected record is missing, return `RECORD_NOT_FOUND`.
- Tool responses must not include credentials, raw filesystem paths, or Azure container internals.

### `listTools` Tool

- `listTools` must return available Review Assistant local tools with name, description, source, optional plugin id, and input schema.
- The tool list must be available to the provider when local tools are configured for a request.

### GitHub Copilot MCP Bridge

- For chat requests with local tools, the agent worker must create a temporary MCP server configuration.
- The MCP server must expose Review Assistant tools over stdio to GitHub Copilot.
- Tool calls must be forwarded from the worker to main, executed by the local tool runtime, and returned to the provider.
- The provider command must allow Review Assistant tools without using a tool availability filter that makes listed MCP tools uncallable.
- Temporary MCP configuration and workspace files must be cleaned up after completion, cancellation, or failure.

## Observability Requirements

- Log when the local tool bridge is ready.
- Log MCP tool list and tool call requests without logging full record contents.
- Log tool execution start and completion with `requestId`, `toolRequestId`, tool name, success state, error code when present, and elapsed duration.
- Log tool request timeouts as errors.

## Test and Harness Requirements

- Unit tests must cover:
  - Tool listing.
  - `readRecord` no-record behavior.
  - `readRecord` trusted-selection behavior.
  - Tool argument validation.
  - Duplicate tool registration errors.
- Integration tests must cover:
  - Main-to-worker-to-MCP tool invocation.
  - Streaming after a successful `readRecord` call.
  - Cancellation cleanup.
  - Unavailable provider gating.
- UI tests must cover:
  - Displayed record context being sent with chat requests.
  - Streamed markdown rendering where tool names appear in assistant output.
- E2E tests must cover:
  - A real Electron flow where a displayed record is read through the local tool and the answer includes record contents.
  - The regression where a tool can be listed but cannot be called.
- Smoke checks must continue to verify preload/main IPC invoke and event pairing.
- Harness CI must run through `make ci` so local and CI entrypoints stay aligned.

## Acceptance Criteria

v0.4.0 is complete when:

- A user can select a record, ask about its contents, and GitHub Copilot can call `readRecord` to answer from the displayed record.
- `listTools` exposes Review Assistant local tools.
- Tool calls are observable through structured logs without record payload leakage.
- Renderer remains UI-only.
- Local tool execution remains behind main-process ownership and storage adapters.
- Deterministic gates pass:
  - `npm run lint`
  - `npm run typecheck`
  - `npm run test:unit`
  - `npm run test:integration`
  - `npm run test:ui`
  - `npm run test:e2e`
  - `npm run smoke`
  - `make audit-harness`
