## Goals

- Remove redundant UI status text for in-progress agent runs.
- Replace split display and feedback configuration files with one unified project config file.
- Add canonical mapping metadata to configuration and expose canonical schema candidates through a dedicated tool.
- Improve tool naming and tool descriptions so behavior is discoverable from tool metadata.

## Agent Running Status UI

- Remove the "Agent is still running..." message from the chat column.
- Keep existing non-text visual cues for active streaming.
- Keep safety behavior that blocks destructive navigation while an agent run is active.

## Unified Project Config

### File name and migration

- Use a single project configuration file named `config/config.json`.
- Hard-cut migration is approved.
- There are no current users, so migration does not need runtime compatibility logic in application code.
- As part of implementation, migrate existing repository fixtures and sample projects from legacy split configuration files to `config/config.json`.
- Remove old split configuration files and all related code paths.

### Naming convention

- Persist project config JSON keys in snake_case.
- Keep internal TypeScript/runtime names in camelCase if that is clearer for code ergonomics.
- Convert between persisted snake_case and internal camelCase at the file boundary.

### Config model

- `config/config.json` must keep the current properties object keyed by JSON Pointer path.
- Each entry supports:
  - path
  - target
  - tab
  - feedback
  - comments
  - presentation
  - mapping
  - edit_mode (optional)
- supports_edit is removed.
- For array schema nodes, edit_mode is omitted.
- For non-array schema nodes, edit_mode may be none, logged, or inline.

### Mapping semantics

- mapping options are:
  - turns
  - request
  - response
  - evidence
  - facts
  - tags
- Each canonical label may be assigned at most once across all explicit mappings.
- No additional semantic validation is required for user-selected explicit mapping beyond uniqueness of canonical labels.

### Config UI popup

- Update the configuration modal to edit all unified config fields.
- Remove supports_edit controls.
- Do not show edit_mode controls for array schema nodes.
- Add mapping controls with uniqueness constraints so a canonical mapping cannot be selected more than once.

## Canonical Schema Mapping Tool

### Rename and scope

- Replace getRecordContainerSchema with a better name that describes canonical schema discovery behavior.
- The replacement tool does not have LIST/INSPECT modes.
- The replacement tool returns canonical mapping candidates for the selected record schema.

### Output contract

- The tool output must include all canonical elements as keys:
  - turns
  - request
  - response
  - evidence
  - facts
  - tags
- Each canonical key returns an object with:
  - candidates: an array of zero or more candidate mappings
- Each candidate includes:
  - path
  - schema

When a canonical element has an explicit mapping, candidates must contain exactly one item.

Implicit candidates must only be returned when no explicit mapping exists for that canonical element.

### Candidate rules

- An empty candidates array means no suitable container or field was found for that canonical element.
- Expected schema shapes:
  - turns: array of objects
  - evidence: array of objects
  - facts: array of objects or array of strings
  - tags: array of objects or array of strings
  - request: string
  - response: string
- Use explicit mappings to narrow implicit candidates.
- If a path is explicitly mapped to one canonical element, do not offer that same path as an implicit candidate for other canonical elements.

## Tool Naming and Descriptions Audit

- Review all built-in Review Assistant tools for naming clarity and description quality.
- Rename tools that do not clearly reflect behavior.
- Upgrade descriptions so they are precise and action-oriented.
- Move durable behavioral guidance from `config/prompt.md` into tool descriptions where practical.
- Keep `config/prompt.md` focused on orchestration policy and interaction flow, not low-level tool contract details.

## Tests and Documentation

- Update unit, integration, UI, and e2e tests impacted by:
  - status message removal
  - `config/config.json` migration
  - mapping uniqueness
  - array edit_mode omission
  - tool rename and new output contract
- Update requirements and guidance docs that mention legacy split configuration files or getRecordContainerSchema.
- Add or update project-level operating guidance in AGENTS.md and/or .github/copilot-instructions.md for:
  - `config/config.json` ownership and naming conventions
  - canonical mapping expectations
  - tool naming and description standards
